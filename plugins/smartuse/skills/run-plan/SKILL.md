# run-plan — tiered execution with a receipt per plan step (v0.2, 2026-10-21)

Why: the kickoff names the deliverables; this skill decides who does each one and proves what it cost. **One receipt per plan step**: tier · model · why · the user's override · outcome · escalation · verification · the agent's real tokens — the thing no router shows. The dial exists because lower models only pay off on small, checkable units.

Manual-only on purpose (`disable-model-invocation: true`): it spends plan usage, so only the user starts it with `/run-plan`. Skills that finish a kickoff should SUGGEST it, never call it.

## Live context
- Now: !`date -u +%FT%TZ || true` · session model: the model answering this turn (never spawn an agent on a stronger one)
- Arguments: `$ARGUMENTS` — a task folder or task.md; `--routing off|safe|aggressive` (default safe); `--units N` (default 3 per "go"); `--yes` skips the dry-run wait (headless only); `--until-done` = run every unit without waiting, keep going until done or a stop reason (see § 3b); it implies `--yes` — the dry-run table is printed, not waited on.
- Repo check command: from the adapter `check:` in `.claude/smartuse.local.md` (human-written; the hook never reads it from routing.json) — required for `--until-done`; without it the gate only tracks unit status. The gate accepts exactly these shapes, verbatim: `npm test` · `pnpm test` · `yarn test` · `bun test` · `pytest [paths]` · `make test` · `make check` · `cargo test` · `go test ./...` · `dotnet test` · `mvn test` · `gradle test`. A `bash <script>` check runs only when pinned in the root-owned `/etc/smartuse/trusted-checks.json` (Linux/macOS, needs sudo): the user runs `bash "${CLAUDE_PLUGIN_ROOT}/hooks/py.sh" "${CLAUDE_PLUGIN_ROOT}/hooks/until-done.py" --trust "bash path/to/check.sh"` in their own terminal, from the repo, and pastes the sudo commands it prints; not available on Windows. Anything else is refused and the gate says so: `npm run x`, `npx …`, `python -m pytest`, flags, pipes, `&&`.
- State dir (where pending.json / routing.json / receipts.jsonl go): !`bash "${CLAUDE_PLUGIN_ROOT}/hooks/py.sh" "${CLAUDE_PLUGIN_ROOT}/hooks/ledger.py" --state-dir --create || true`

## State writes — one Bash call each, never Write / Edit
routing.json and pending.json live in the state dir under `~/.claude/`, which Claude Code treats as a sensitive path: Write / Edit there prompt every time and are denied headless. Write them only through the hook script (`Bash(bash *)` runs it); every call prints what it wrote:
- **The plan:** `bash "${CLAUDE_PLUGIN_ROOT}/hooks/py.sh" "${CLAUDE_PLUGIN_ROOT}/hooks/ledger.py" --put routing.json '<the plan JSON>'` — the whole object as ONE single-quoted argument on one line (Claude Code refuses JSON in a heredoc; an apostrophe inside a value is `\u0027`) → prints `put routing.json → <path in the state dir>`. `put refused: <reason>` = nothing was written: fix the JSON and run it again. `--put pending.json '<json>'` works the same.
- **One step:** `bash "${CLAUDE_PLUGIN_ROOT}/hooks/py.sh" "${CLAUDE_PLUGIN_ROOT}/hooks/ledger.py" --unit <id> key=value …` — e.g. `--unit 2 status=running` · `--unit 2 status=pass 'check=12 passing' 'files=["src/a.js"]'`. When a value is more than one plain word, single-quote the WHOLE `'key=value'` word (Claude Code refuses `key='{…,…}'` as brace expansion; use double quotes for a text with an apostrophe). A value that parses as JSON is stored as JSON (`3`, `true`, `null`, objects, lists), anything else as text. It prints the step's new line.
- **The run:** the same command with `--run key=value …` — `--run 'needs_human=which rounding rule?'` · `--run active=false`. **Read back:** the same command with `--get routing.json`.
- The hooks' fields are never yours: `agent_calls` · `agent_input` · `agent_output` · `agent_models` · `agent_by_model` · `agents` (the SubagentStop hook's real tokens) and `blocks` · `last_block` · `check_error` (the gate's). `--unit` / `--run` refuse them, and a re-put of the same run (same `task` and `started_at`) keeps them.

## 0. Read the kickoff
Read task.md: § 5 deliverables (the units), § 4 constraints and rabbit holes (restated in every brief), § 7 open questions, § 8 verification. No task.md → "run `make-prompt` first" and stop.

**Open questions are not all blockers.** make-prompt writes a kickoff that assumes and lets the user correct by exception, so:
- A question whose answer the kickoff already gives as an `assumed:` default (a route, a column set, a date, a file layout) is **answered for now**: proceed on the default, write one dated line in `decisions.md` ("proceeding on assumed <X>; correct by exception"), and list it at the end under **Confirm**, not under NEEDS YOU.
- A question with **no default**, or one in a rule-gate area (money, security, shared servers or procedures, another person's file that the plan would edit), **blocks** the units that depend on it — say so, do not guess.
- Never block every unit on a question the kickoff has a default for. A run that ends with 0 steps done and a NEEDS YOU about an assumed value is a failed run.

## 1. Tier each unit (the session model decides, never a hook or a keyword rule)
| Tier | What belongs here | Who runs it |
|---|---|---|
| **judgment** | design options, root cause, anything on money / security / shared procedures / other people's files, writing or changing the plan | the session model, in this conversation (no agent) |
| **build** | a well-specified change with a runnable check (test, build, script, screenshot compare) | `safe`: the session model via a fresh foreground agent · `aggressive`: one tier below the session model |
| **mechanical** | greps, caller inventories, file lists, doc updates, test-data generation, key or translation checks, formatting | the cheapest model your plan offers (`haiku` where available) via a foreground agent |
| **verify** | review a delegated unit's output against its spec, gaps only | a fresh agent, one tier below the session model (`sonnet` where available) |
`--routing off`: every unit on the session model, receipts still written — this is the A/B baseline. Rules: a unit without a runnable check is never `mechanical`; nothing is routed to a model stronger than the session's; a blocked unit stays blocked.

## 2. Dry run (always shown, then WAIT for "go" unless --yes or --until-done)
Put the plan into the state dir with `--put routing.json` (see State writes — never inside the repo; if the live-context state-dir line is empty, run `bash "${CLAUDE_PLUGIN_ROOT}/hooks/py.sh" "${CLAUDE_PLUGIN_ROOT}/hooks/ledger.py" --state-dir --create` yourself — it prints the dir and creates it): `{"active":true,"task":"<name>","dial":"safe","started_at":"<now>","units":[{"id":1,"title":"…","tier":"mechanical","model":"haiku","why":"<one line>","budget_turns":15,"check":"<the runnable check>","blocked_by":null,"status":"pending","override":null,"escalated":false,"verify":null}]}` (with `--until-done` add `"until_done":true`), and print the same as a table: `# · unit · tier · model · why · budget · check`. Then: `Say "go" to run the first <N>, "go all", or "retier 3 build" to change a row.` Nothing runs before that — except with `--until-done`, which implies `--yes`: print the table, then go straight to § 3b. A retier is recorded on the unit, never silently applied: `--unit 3 tier=build model=<model> 'override={"from":"mechanical","to":"build","by":"user","at":"<now>"}'` — the receipt shows `mechanical→build`.

## 3. Execute, one unit at a time, FOREGROUND
For each unit in order:
1. `--unit <id> status=running` (only one unit may be running at a time — that is how the SubagentStop hook knows which plan step the agent's tokens belong to). Spawn ONE Agent (foreground — the user sees the task card and tool count) with `model` per the table and a brief of ≤ 40 lines: the unit's spec and check · the constraints + rabbit holes from § 4 · the files it may touch (and only those) · "you cannot ask questions: write `unknown: <what> → <who>` instead" · "report: what you did, the check's output verbatim, files changed, unknowns" · the turn budget.
2. On return: `--unit <id> status=<pass|fail|blocked> 'check=<first line of the check output>' 'files=["<file>", …]'` — the step's fields are its receipt (the archive under `runs/` keeps them). The SubagentStop hook has already attached the agent's real calls and tokens to the running unit (`agent_calls`, `agent_input`, `agent_output`, `agent_models`, `agent_by_model`, `agents`) and written its own line to `receipts.jsonl` — never estimate tokens yourself; those fields are the hook's, `--unit` cannot touch them.
3. `fail`, or a blocking `unknown:` → **escalate once**: `--unit <id> status=running escalated=true model=<one tier up>` (never above the session model), re-run the unit with the failure pasted in (the receipt keeps both agents' tokens on the step), then step 2 again. Still failing or blocked → stop the batch and go to § 4 Close anyway (the receipts and the ledger line must exist even for a blocked run); do not loop.
4. **Verify** every delegated `build` unit: `--unit <id> status=running` again, then a fresh agent (verify tier) gets the diff (`git diff` / `svn diff` of the unit's files) + the unit's spec: "list only gaps that affect correctness or the stated spec; no style". Gaps → fix on the build tier once → re-verify once. Record the verdict and the status together: `--unit <id> status=pass 'verify=no gaps'` (or `'verify=gaps fixed'`; `'verify=gaps open'` with `status=blocked`). Judgment units are verified by the user, not by an agent (`verify` stays null).
5. After each unit print ONE line: `unit 2/5 done · mechanical/haiku · check passed · next: unit 3 (build)`. That line is the visibility rule — never run silently.
Stop after N units (default 3) and ask "go" again, so the user can read the receipts between batches.

## 3b. `--until-done` — the lazy-CEO loop
The plan you put in § 2 carries `"until_done": true` and `"status": "pending"` on every unit (if it does not: `--run until_done=true` before the first unit). The check command is read by the gate from the human-written adapter (`check:` in `.claude/smartuse.local.md`) — you cannot set or change it from routing.json; if the adapter has none, the gate only tracks unit status. Then:
1. Run units in order with no "go" between batches. After each unit set its `status` (`--unit <id> status=pass|fail|blocked`, § 3.2) and print the one-line progress message.
2. The `until-done` Stop hook refuses to end the turn while any unit is pending / running / failed or while the check command fails, and tells you what is left. Keep working; do not argue with the gate.
3. **Stop reasons — the only ways out:** (a) every unit is pass or blocked AND the check passes; (b) a unit needs the human for a question with **no assumed default** (or a rule gate): write the exact question with `--run 'needs_human=<question>'` and make it the FIRST line of your final message (`NEEDS YOU: …`) — an assumed default is not a stop reason, see § 0; (c) a unit failed twice (escalation used) → `--unit <id> status=blocked 'note=<why>'`, continue with units that do not depend on it; (d) a rule gate (a file owned by someone else, a shared server, money or security paths) → `needs_human`; (e) the gate has blocked 6 times → it lets you stop; say what is left.
4. Never commit. The final message: `NEEDS YOU` line if any (real blockers only), then the receipts table, then **Confirm** (the assumed defaults you proceeded on, one line each), then "what the human should look at first".
In an interactive session the user may also set `/goal <§ 8 acceptance>`; in headless use the CLI caps and the permission flag a real run needs (agents, file writes and the hooks' own commands): `claude -p "/smartuse:run-plan <task.md> --until-done" --permission-mode bypassPermissions --max-budget-usd N --max-turns M` — bash-guard still fires in bypass mode.

## 4. Close (always — after a finished batch, a stop, or a block)
- Tick the units' boxes in task.md; add a dated line to `decisions.md` / `## Decisions` for every escalation or retier.
- Print the receipts table with `bash "${CLAUDE_PLUGIN_ROOT}/hooks/py.sh" "${CLAUDE_PLUGIN_ROOT}/hooks/ledger.py" --receipts` (one row per plan step: `# · step · tier · model · override · outcome · esc · verify · calls · in · out · check`, plus the summary line with the agent-output share by model, e.g. `agent out by model: fable 40% · haiku 45% · sonnet 13%`). Paste it verbatim — the tokens are the SubagentStop hook's and the by-model shares are the tool's, never an estimate: quote that line, do not compute a split of your own — and add only the one-line comparison: "with `--routing off` every step would have run on the session model."
- `--run active=false`, then `--put pending.json` (State writes) with `{"skill":"run-plan","task":"<name>","mode":"<dial>","started_at":"<routing.started_at>","self_check":"<passed>/<units>","notes":"<escalations>"}` for the ledger. The Stop hook writes the ledger line and archives routing.json under `runs/` — `/smartuse:receipts <task>` shows it later.

## Rules
- Foreground only. Never the Workflow tool from this skill — multi-agent runs need the user to type the request themselves ("use a workflow"); offer that in one line when ≥ 3 units are independent.
- The session model tiers; a brief restates the rules because agents do not inherit them; agents never ask the user.
- One escalation, one re-verify, then stop and report. No silent retries, no second batch without "go".
- Nothing outside the unit's files; no commits (the user's commit procedure does that, and `living-docs` runs after it).
