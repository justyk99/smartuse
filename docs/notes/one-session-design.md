# One session that delegates — the main pattern (proposal, 2026-10-22). For the author.

Source: the incident "The 'step done' message that never arrived" (anonymised; the course's case study 8), in the same two-session setup as "The relay that turned photos into words" (case study 7, `relay-design.md`). A cloud **manager** session planned and reviewed; a laptop **builder** session coded and rendered; the owner pasted the manager's prompts into the builder and expected a ping when a step was done. The builder finished at 20:57 and sent "step done" with its own messaging tool; the message never arrived. The manager had stopped its git watcher earlier to save tokens and did not re-arm it after the hand-off. It learned the step was done from the owner, while the builder's push from a minute earlier sat on the remote the whole time.

The same day smartuse's own pair did the same: the laptop session's test report, sent at 12:39 UTC to a session name that does not route to a cloud session, never arrived; the planner found it by reading the laptop session's transcript at 13:08.

Status: **M1, M2 and M3 built (2026-10-22), M4 and the rest still proposals.** Each part below is the cheapest mechanism that enforces its rule, with the test that replays the incident. Build order at the end.

## The pattern
- **One orchestrator session runs where the files and tools live** (here: the laptop with the GPU renderer). The owner talks only to it, from the phone through Remote Control.
- **It keeps the judgment:** the plan, the reviews, the owner's taste.
- **It hands the mechanical work down, cheapest first:**
  1. **A command** (a render, a conversion, a test run) → a background task. Done = its exit code and its output files, checked in the session. No model tokens while it runs, and its completion wakes the session.
  2. **Model work without judgment** (bulk edits, tests written to a spec, a conversion that needs reading) → a subagent on a cheaper model with a full brief: the spec, the check, the files it may touch, every input as an absolute path ("open each one"), a turn budget. Then a verify step (the check, or a fresh agent).
  3. **Judgment** stays in the session.
- **Why this removes both incidents:** subagents and background tasks share the filesystem, so a photo is a path and never a description (case 7). Results return to the same session, so there is no "done" message to lose (case 8). One context instead of two means no relay text written twice and no hop to drop a file or a signal.
- This is already run-plan's loop: units, tiers, verify, a receipt per step, the until-done gate. The proposal makes it the front door and closes the gaps below.

## Trade-offs, said once
- The orchestrator lives on the laptop, so a sleeping or closed laptop is a stopped session (the same lesson). Keep it awake while it runs. A cloud session does not sleep, but it does not have the renderer either.
- One context grows. Keep the heavy reading in subagents, and run long renders as background tasks, never as an agent waiting on a process.
- Subagents cannot ask questions; unknowns come back as `unknown: … → who` and the orchestrator asks the owner.
- A second session is still right when the work needs another machine (a tool or OS that exists only there, a server). Then the three rules hold: "done" is a push, a file or an exit code, and a chat message is a courtesy; arm a watcher after every hand-off; and prefer one session wherever the machine allows.

## M1 — `watch.py`: the watcher as one command (rules 1 and 2) — BUILT 2026-10-22
- `bash "<plugin>/hooks/py.sh" "<plugin>/hooks/watch.py" --git <remote> <branch> [--path <file>] [--since <sha>] [--every 60] [--max 4h]` polls `git ls-remote` (no model tokens, one small request a minute) and exits 0 when the branch head moves (with `--path`, once that file exists at the new head), printing `pushed <sha7> "<subject>" · <path>`. `--file <path>` waits for a local file. At `--max` it exits 3 with `no signal after 4h`, and after three failed polls in a row it exits 4 with `cannot reach <remote>: <git's error line>`, so the session is woken either way and never waits silently. There is no `--pid`: a command is run as the background task itself, and its own exit is the signal.
- `--since <the hand-off's commit>` makes that commit the baseline, so a push made before the watcher started still fires: a watcher armed late, or re-armed after a restart killed the first one (this session's own container restarted the day it was built).
- The session runs it as a background task (Bash `run_in_background`); the task's completion notification is the wake-up. An exit 0 always carries one line; an empty exit 0 means `py.sh` found no Python and nothing was watched.
- **Test that replays the incident (in the suite):** a bare fixture remote; the watcher starts; the builder fixture pushes a commit adding `docs/M3-RESULT.md`, and its "step done" message goes nowhere. Result: exit 0 within one poll, naming the commit and the file. In the incident nothing was polling. Also covered: no push → exit 3; a push without the file under `--path` → still waiting; a dead remote → exit 4; armed late with and without `--since`. `hooks/tests/watch-test.sh`, 63 cases.

## M2 — the wait gate: "if nothing will wake you, you are stopped" (rule 2) — BUILT 2026-10-22
- **Mechanism:** `hooks/wait-gate.py`, a Stop hook between until-done and heartbeat (timeout 10; 0 tokens; stdlib, no subprocess, Python 3.9+). It reads the session transcript once and blocks the end of the turn, once, when a hand-off is open and nothing is armed to wake the session.
  - **Scope** = the records after the last genuine human prompt: a `user` record with real text that the harness did not inject. On 2.1.308 that is no `isMeta`, no `isCompactSummary`, and `turnOrigin` / `origin.kind` `human` or `sdk` (or absent): what the harness injects — a task notification, a message from a peer, a scheduled wake-up, a cron — is not a prompt, so a check-in that finds nothing does not close the hand-off it was set for; a message the owner typed mid-turn is an `attachment` `queued_command` with `origin.kind` `human`; the local-command echoes and the interrupt marker are not prompts; a slash command is.
  - **Hand-off open** = in scope and not answered: a `mcp__claude-code-remote__send_message` call that did not fail; a `SendMessage` whose `recipient_kind` is not `agent` (and not a background agent of this session, by id or name); or the final reply matching a hand-off phrase. The phrase test is a **pattern match**, prose only (code is ignored): `paste this / it / that / the following / the line / the prompt / the brief … into / in …` (not into a file, a console, a terminal or a shell, a chat or a reply, Slack, an issue or a PR: those are instructions for the human), `I'll / I will ping / notify / message / update you`, `tell you` (not `tell you what / why / how / about / that`), `let you know`, `check / come / report back`. **Answered** = after it came a task notification with status `completed` (not the echo of a task the session stopped itself with `TaskStop`, not a failed one such as watch.py's "no signal") or a message from another session or agent. Without this the designed flow would block itself: arm the watcher, hand off, wake on its notification, review.
  - **Watcher alive** (the whole transcript): a background Bash (`run_in_background`, or moved to the background at its timeout), a `Monitor`, a background `Agent` or `Workflow`, unless a later `TaskStop` names its task id or a notification for its task id / tool-use id has a final status; a `send_later` with `fire_at` ahead; a `ScheduleWakeup` whose delay has not passed; a `CronCreate`, `create_trigger`, `subscribe_pr_activity` or `watch_url` unless deleted, unsubscribed or unwatched later. The Stop input's own `background_tasks` / `session_crons` count when they hold a live entry. Any live task counts as the watcher.
  - **PASS** (exit 0, nothing printed): no hand-off open (wait.json removed) · a watcher alive (`watching`) · the reply has a line starting `STOPPED:` (`stopped`) · the adapter says `wait_gate: off` · the gate already blocked once for this scope.
  - **The block** (the Stop-hook JSON until-done prints, a reason of at most 6 lines): `wait gate: you handed off at 20:41 (send_message to session_…) and nothing will wake you.` · `No watcher is armed: the watcher started at 20:30 was stopped (background Bash).` · then the fix: arm one in the background, `bash "<plugin>/hooks/py.sh" "<plugin>/hooks/watch.py" --git origin <branch> --path <result file> --since <the commit you handed off at>` (`<plugin>` absolute from the hook's own location, `<branch>` read from `.git/HEAD` when it is a plain name), or schedule a check-in, or end the reply with `STOPPED: nothing will wake me; <who> must.` Once per scope: a marker (`wait-block.json`) names the session, the last human prompt and the last answer, so the second Stop passes and a hand-off after a later wake-up is gated again. Never a trap.
  - **Outcome** in `~/.claude/smartuse/projects/<key>/wait.json`: `{at, state: watching | stopped | blocked, what, since, watcher: {kind, id, armed, state}, session_id, scope}`; removed when no hand-off is open. **The hand-off a Stop found stands until something answers it:** a later Stop in the same scope (the same session, last prompt and answer, the `scope` field) whose reply does not repeat it — it says `STOPPED:`, or it armed a watcher, or it just ends — carries the entry over (`stopped`, or `watching` when something is armed; the hand-off's text and time are kept), so the second reply of a blocked turn does not turn the status line back to "waiting on you". A new prompt or an answer ends it. `wait_gate: off` in `.claude/smartuse.local.md` (human-only: file-guard) switches the gate off.
- **Checked on real Claude Code 2.1.308 data** (shapes only; every fixture is synthetic): the tool_use / tool_result blocks; the background-Bash result text (`Command running in background with ID: …`, or `… moved to the background (ID: …)` at the timeout); the task notification as a `queue-operation` enqueue, a `user` record (`turnOrigin` `task_notification`) and, when absorbed mid-turn, an `attachment` `queued_command`; the one real `TaskStop` left no notification for its task (the stop is the end signal; an echo, if a version sends one, is no answer); a Monitor event has no `<status>`; `TaskStop {task_id}`; `SendMessage` with `recipient_kind`; `send_later` → `{"fire_at": …}`; a failed `send_message` has `is_error`; a Stop-hook block comes back as an `isMeta` user record `Stop hook feedback: …`. **The Stop input** carries `last_assistant_message`, `background_tasks [{id, type, status, description, command}]` and `session_crons`, and **the final assistant message is already in the transcript when Stop fires** (two headless probes, re-read 0.5 s and 1.5 s later: unchanged); the gate prefers `last_assistant_message` when the input has it and reads the transcript otherwise. Not available to check: a real `ScheduleWakeup`, `CronCreate`, `create_trigger` or `watch_url` call (their shapes come from the binary's schemas and the tool descriptions) and a `SendMessage` with `recipient_kind` other than `agent`.
- **Live checks:** headless sessions (haiku, under a cent each; about $0.04 for the seven of the whole job, the two Stop-input probes included). With only this hook: the model replied "Paste this into the builder, and I'll ping you when it's done" with nothing armed → blocked (the reason came back as `Stop hook feedback: …`) → it ended with `STOPPED: nothing will wake me; …` → the second Stop passed. That run also showed the gap the carry-over closes: the `STOPPED:` reply did not repeat the phrase, so the entry was removed and the status line would have read "waiting on you". With the plugin's own hooks.json (`--plugin-dir`) and a debug hook that renders `heartbeat.py --line` after each Stop: after the block `smartuse · STOPPED · handed off 18:07 ("Paste this into the builder") — nothing will wake this session` (wait.json `blocked`); the model's next reply neither said `STOPPED:` nor repeated the phrase ("Nothing is pending on my side. …"), the second Stop passed and the same line stayed (wait.json `stopped`, what and time kept). A reply "Paste this into your terminal: ls -la" was not blocked (no wait.json, the line `waiting on you · 2s`).
- **Replay of the incident (in the suite):** a fixture of the manager: a background watcher armed, stopped with `TaskStop`, then "Paste this into the builder: … I'll ping you when it's done." → **blocked**, the reason names the stopped watcher and the hand-off. Also covered: a watcher armed after the hand-off, a `STOPPED:` reply, no hand-off, the second Stop, `SendMessage` to a subagent / another session, `send_message` (and a failed one), a watcher finished before the hand-off, `send_later` ahead / behind, a hand-off before the last human prompt, every kind of watcher alive and ended, the hand-off answered by a notification or a message, which user records start a scope, the phrases matched and not matched, garbage input, `wait_gate: off`, the 6-line reason and its command (bash-guard allows it), the state dir equal to ledger.py's. `hooks/tests/wait-gate-test.sh`, 187 cases; 57 mutations of the gate (each rule switched off or broken in turn), each caught by the suite once the gaps they exposed were closed. Replayed over this machine's real transcripts (156 turn ends, my own probes included): the only blocks are the live probes' (3); the 11 other open hand-offs all had a watcher alive (a `send_later` check-in, a background task or agent).
- **Not built:** the "push of a brief for another session" trigger (nothing in the transcript says that a push is a brief) and the builder-side twin ("push first — the push is the done-signal"; lower priority, rule 1).
- **Limits:** the reply trigger is a pattern match; any live background task counts as the watcher, so a watcher on the wrong branch or a long test run passes the gate; a `send_message` that only reports ("step done") is a hand-off too, so a builder is blocked once and answers `STOPPED:`; a hand-off answered by an unrelated notification is not seen as open; a one-shot `CronCreate` / `create_trigger` counts until its time, a Monitor until its end notice; an instruction for the human that the exclusions do not know (`paste this into Postman`) blocks once, and so does a `SendMessage` to a teammate whose answer would wake the session (no real `recipient_kind` other than `agent` was available to check); a scheduled check-in counts as alive until its time, yet delivery can fail — on 2026-10-22 a `send_later` check-in into the planner's own session was refused when it fired at 15:27 (ACCESS_DENIED), so a background watcher in the same session (`watch.py`) is the surer wake-up and the block message lists it first.

## M3 — the status line tells waiting from stopped (rule 2, for the owner) — BUILT 2026-10-22
- `heartbeat.py --line` (and `--statusline`, `--json`) reads wait.json at render time, from the same state as M2, when the turn is over and wait.json is from this session and not older than the last UserPromptSubmit (`prompt_at` in status.json): `STOPPED · handed off 20:41 (builder) — nothing will wake this session` (state `blocked` or `stopped`; `--json` state `stopped`) or `waiting on builder · watcher armed 20:41` (state `watching`; `--json` state `waiting_on_handoff`) in place of `waiting on you`. HH:MM is the local clock. A tool running, an agent running, a permission prompt and `NEEDS YOU` rank above it as before; a new prompt makes last turn's file stale; a wait.json it cannot read or does not know is ignored.
- **Test:** `hooks/tests/heartbeat-test.sh` +34 cases: the line for each state, no `what`, no watcher time (and the watcher spelled as a stamp, as `HH:MM`, or with `at`), another session's file, a file older than the last prompt, a corrupt file, an unknown state, `--json`, `--statusline`, the ranking against tool / agent / permission prompt / `NEEDS YOU`, `prompt_at`.

## M4 — steering into one session (rule 3): make-prompt and run-plan, no new skill
- **make-prompt:** the ground check answers "where do the files and tools live?": is the repo here, and do the tools the ask names resolve (`command -v <tool>`)? The kickoff gets a `Runs on:` line. The self-check line "right repo" becomes "right repo and machine (files and tools here)", so the list stays at 14. When the ask describes a relay ("I'll paste your prompts into my laptop session", "ping me when it's done"), the hand-off says: run this kickoff on <machine> as one session with run-plan; use a second session only for another machine, with its done-signal and a watcher.
- **run-plan:**
  - § 0 pre-flight: each unit's check command and tool must resolve here, and each input file must exist. A unit whose tool is elsewhere shows `needs-machine: <tool> not found here` in the dry-run table. A plan whose work is elsewhere stops with "run this plan on <machine>", not a relay from here.
  - A new `command` tier below `mechanical`: one command, no model, run as a background task; done = its exit code and output files.
  - Briefs carry every input as an absolute path.
- **README:** lead with the pattern in one line — "one session where your files and tools are: it keeps the judgment and hands the mechanical work to cheaper subagents, each with a brief and a check" — with the two-session rules under "When you need a second machine".
- **Tests that fail on this incident** (eval cases, model-graded):
  - `kickoff-two-sessions`: the prompt is the incident's setup ("plan the next step; I'll paste your prompt into my laptop session, which has the renderer; ping me when it's done"), in a repo where the renderer is not installed. Graders: a regex for `Runs on:`, plus a judge. To pass, the reply either moves the work to one session on the laptop with run-plan, or keeps two sessions with the push as the done-signal and a watcher armed. Either way it never promises a ping with nothing armed. The incident's reply ("paste this into the builder; I'll ping you when it's done") scores 0.
  - `run-plan-wrong-machine`: a task.md whose units render with a tool that is not on this machine → the dry run shows `needs-machine` and no unit starts.

## What this changes in the relay guards (case 7)
One session removes most of their reason. When photos are paths, there is no relay to guard (rules 1, 2 and 5), so those stay proposals for the second-machine case. The paid-call guard (rule 4) still matters: a cheap subagent can spend money as fast as a planner can.
