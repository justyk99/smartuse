## 4. Features

### F1 · the term scan reads every line whole (lane B · 1 day) — item (a) + the UTF-8 item
- **Evidence.**
  - History keeps one pattern per line: `term-scan.py:103–107` breaks after the first pattern that matches.
  - Private patterns come last (`:83`, `GENERIC + private`). So a private term on a line with a generic hit is not counted.
  - `mask()` stars only the hit itself and prints 30 characters each side as they are (`:48–52`). So that line's excerpt shows the term in clear. The tree scan does count both (`:55–62`, its `break` leaves only the `finditer` loop), but the generic hit's excerpt shows the term too.
  - Commit messages are never read: the format is `commit %h %s` (`:95`), and that line is taken as the label and skipped (`:98–100`). The body is not in the format.
  - File paths are never read: history skips `diff --git` (`:101`); the tree reads contents only (`:85–93`).
  - Bytes that are not UTF-8 are lost silently: history decodes with `errors="replace"` (`:95`), the tree with `errors="ignore"` (`:90`). A term saved as cp1252 cannot match.
  - A binary diff (git prints `Binary files … differ`, a UTF-16 file included) is skipped without a word.
- **Fix.**
  - History lines go through the same per-pattern loop as the tree. Private patterns go first (`private + GENERIC`).
  - Each excerpt stars every character that lies inside any private match on that line, the generic hits' excerpts included.
  - The history format also carries the message, indented so a message line cannot pass for a `commit`/`diff` line (for example `commit %h%n%w(0,4,4)%B`). The label stays `history@<hash>`.
  - Paths are read if D-YK21 says so: the tree's tracked paths, and history's `diff --git` lines.
  - Git output and files are read as bytes. A line that is not valid UTF-8 is scanned twice, as UTF-8 with replace and as cp1252 with replace; the same hit is kept once. A line with NUL bytes is also scanned with them removed (the ASCII letters of UTF-16 text).
  - The summary line keeps its start and adds `(N private)` after the hit count. Two clauses appear only when not zero: `· N lines not UTF-8` and `· M binary diffs not read`.
- **Acceptance (the user does).**
  1. The maintainer types `python scripts/term-scan.py --history --max-hits 1000000`, bare, as `CLAUDE.md:8` has it. The summary says how many hits are private.
  2. A line holding an e-mail and a private term is reported as `private#n`. The term never appears in the output.
  3. A private term in a commit subject is reported with `history@<hash>`.
  4. A term saved in cp1252 is found, and the summary says how many lines were not UTF-8.
- **Unit (red first, `term-scan-test.sh`, temp repos, invented terms).**
  - r1, history: one committed line holding the suite's flagged e-mail (the address at `term-scan-test.sh:28`) and `zebrafish` gives a `history@` `private#1` hit (red: the e-mail wins). This plan spells no address, so it adds no hit of its own.
  - r2, tree: the same line; the e-mail hit's excerpt holds no `zebrafish` (red: it does).
  - r3: a commit subject holding the term (red: the subject is skipped).
  - r4: the term `zébrafish` in the list, the bytes `z\xe9brafish` in a tracked file: a tree and a history hit, plus the not-UTF-8 clause (red).
  - r5: `--max-hits 1` on the r1 line keeps the private hit (red: generic patterns come first).
  - r6: a UTF-16LE file holding the term: a tree hit, and history counts one binary diff (red).
  - r7, if D-YK21: a tracked file named `zebrafish-notes.txt` (red).
  - The 7 existing cases (`:12–34`) stay unchanged, and one check proves the term is in no output.
- **Integration.** The script over this repo's whole history, plain `python`, no variables.
  - Private hits must be 0, and must agree with the per-line re-check of the 0.7.1 push (a scratch script; rebuild it from `next-release-brief.md:13` if it is gone).
  - The new generic hits (from messages and paths) are listed by pattern name for the maintainer.
  - **A private hit stops the step.** The builder reports the pattern number and the label only, never the text. The maintainer decides; no history rewrite and no push without the word.
- **Interactive.** The publish command of `CLAUDE.md:8`, typed as written on the laptop. Then a scratch repo with an invented term beside an e-mail and in a commit subject: both are reported, masked.
- **Must not change.**
  - Exit codes 0, 1, 2 (`:122`), the patterns (`:16–26`), `load_private` and the terms file format (`:31–45`).
  - `--no-private`, `--repo`, `--max-hits` (default 400, `:78`), the 30-character window (`:51`).
  - The labels `<file>:<line>` and `history@<hash>:<line>`, and the CI step (`ci.yml:55`).
  - A private term is never printed. No new import; no allowlist reads this script.
- **Switch:** none. The cp1252 second reading is a fixed choice, not the console's code page.

### F2 · making a state folder keeps the paid count (lane A · 1 day) — item (b)
- **Evidence.**
  - `fit_key` (`heartbeat.py:164–203`, copied byte for byte at `bash-guard.py:2021`, `ledger.py:214`, `recall.py:81`, `until-done.py:73`, `wait-gate.py:130`) keeps an existing full-key folder on Windows while `dirlen + 1 + 26 <= 259`, or at any length while long paths are on (`:193`).
  - A project on the short key (state folder past 194 characters) therefore moves to a fresh folder once anyone `mkdir`s its full-key folder. The paid counter stays behind, so the count restarts (`SECURITY.md:46`, `ROADMAP.md:101`, `next-release-plan.md:166`).
  - `owner-file` (`bash-guard.py:131`) does not match the folder name, so the shell may make it.
  - On Linux and macOS a short key arises only past 255 characters, where the full-key folder cannot be made (`fit_key` rule 4), so the reset is Windows-only.
- **Rule (D-YK19, recommended option).** The short-key folder's counter wins. Past the length test, an existing full-key folder is kept as today, unless the short-key folder holds `paid-runs.json`. Only the hook writes that file: `owner-file` (`bash-guard.py:131`) and `file-guard` (`file-guard.py:27`) refuse plain writes of it. Order:
  ```python
  long = len(full) > KEY_MAX or (nt and dirlen + 1 + NAME_ROOM > WIN_PATH_MAX)
  if not long: return full                      # common path: no stat, no sha1 (today :192 stats every call)
  s = short()                                   # one sha1
  if isdir(base/full) and (not nt or dirlen + 1 + KEPT_ROOM <= WIN_PATH_MAX or long_paths()) \
     and not isfile(base/s/"paid-runs.json"): return full
  return s
  ```
  This gives today's answer for every case except the new clause (the builder proves it with the existing table, below). It reads names, never content.
- **Acceptance (the user does).**
  1. On Windows, in a repo whose state folder would be 220 characters, the owner's adapter go is `render.py x 3, cap RM1`. Run 1 runs. A shell then `mkdir`s the full-key folder. Run 2 is refused with "run 1 of 3 is done; the batch waits for the owner's test ok". The count survived; today run 2 runs as a new run 1.
  2. In a repo used before 0.7.1, whose kept full-key folder has no short-key counter beside it, `/smartuse:receipts` still lists the old runs: no folder moved.
- **Unit (red first, the `fit_key` table in `wait-gate-test.sh:1324–1457`, nt as a parameter, temp base, fake winreg `:1350–1365`).**
  - g1, nt: an existing full folder at dirlen 220, and a short folder holding `paid-runs.json`, gives the short key (red: full).
  - g2, nt: the same without `paid-runs.json` gives full (pins D7a).
  - g3, nt with the fake switch on: an existing folder at 248 and a short folder with a counter gives short (red).
  - g4: no full folder and a short folder with a counter gives short (pins).
  - g5, not nt: a faked existing 300-character folder and a short counter gives short (red; the rule stays the same on both).
  - g6: a 20-character key whose folder exists makes no `isdir` call and no sha1 (a recording stand-in, the `:1400–1401` shape).
  - g7: a kept folder costs one sha1 run.
  - Every row now at `:1383–1426` stays green, and the six copies stay identical (`:1342`).
  - `same6` (`:1284–1288`): with a short-folder counter and a made full folder, all six hooks name the short folder.
- **Integration.** `paid-guard-test.sh` §39b, beside §39 (`:2100–2129`). On Windows: a real project folder whose state folder is 220 characters, adapter go `render.py x 10, cap RM5, test ok`.
  - Run 1 is counted in the short folder. The test then `mkdir`s the full-key folder.
  - Run 2 shows `used 2` in the short folder, and the full-key folder stays empty (red: `used 1` in the full-key folder).
  - Elsewhere the case is skipped (no short key can meet a makeable full folder), and says so.
- **Interactive.** Headless Claude Code with the worktree's plugin, temp `HOME`, a 220-character project path on the laptop. It needs the owner's adapter line, which the guard rightly refuses to Claude (`next-release-plan.md:113`). So the owner writes it (optional, 1 minute), and the run then follows acceptance 1. Without it, the suite case stands in, said as synthetic.
- **Must not change.**
  - The key of every path that works today (the table rows above, the suites' `key()` at `ledger-test.sh:10`).
  - `WIN_PATH_MAX`, `NAME_ROOM`, `KEPT_ROOM`, `KEY_MAX`, `TAIL`, `HASH`. `fit_key` never raises.
  - `hashlib` and `winreg` stay inside `fit_key`; no new import, so the four allowlists (§3) stay as they are.
  - `ledger.py --state-dir`'s output, `legacy_dir` (`ledger.py:275`), one Python start per hook.
- **Switch:** `WIN_PATH_MAX` 259 was measured with `LongPathsEnabled` = 0 (0.7.1 E1). The table uses the fake winreg, so it holds on any machine. A 220-character folder can be made and written with the switch either way.

### E1 · the ledger drop, traced (after F4's T2, laptop alone · 1–2 hours, no build) — item (e)
- **Evidence.**
  - `on_stop` claims `pending.json` by rename (`ledger.py:307–311`). A failed read of the claimed file deletes it and returns (`:312–316`).
  - 0.7.1 E2 (`next-release-plan.md:112`): 4 rounds in 1,000 left no line. Run 1's three failed renames were `errno 13 / winerror 5` with the source gone. Its reads were not logged then.
- **Hypothesis H1 (from the code and E2).**
  - On Windows a rename opens its source for delete. Hook B can hold such a handle while hook A's rename wins.
  - A's `read_text` then fails with a sharing violation (winerror 32), because Python's `open` shares read and write but not delete. A deletes the claimed file (`:315`).
  - B's rename then fails on a deleted file (winerror 5). Both hooks return, and no line is written.
  - E2's "read: FileNotFoundError" rounds are the other order: B's handle renamed the file a second time, and B wrote the line.
- **Alternatives.** H2: the dedupe at `:359–364` hid a line (only if two rounds share session and task within 60 s). H3: both hooks saw no file at `:304`.
- **Steps.**
  - E1a: the E2 wrapper (session scratchpad, temp `HOME`, `ledger.py` unchanged), 1,000 rounds of the `ledger-test.sh:49–52` shape, each round with its own task name. It logs per hook (pid, a monotonic ns time) the result at `:304`, `:309`, `:313`, `:315`, `:362` and `:367`, with errno and winerror.
  - E1b: a deterministic try. A stdlib `ctypes` script holds `pending.json` open with delete access and full sharing, as a rename in progress does, while one Stop event runs, then lets go. H1 predicts no line.
- **Result.** In §10: drops, each drop's two logged paths, H1 confirmed or not. If confirmed, the next release's fix shape goes to ROADMAP: the read retries a sharing violation 5 times, 20 ms apart (the `write_json` shape, `ledger.py:175–181`), and deletes the claimed file only when its JSON is bad. E1b becomes that fix's red case.
- **If unclear.** Process Monitor (Sysinternals, free, admin) filtered on `pending.` during 200 rounds, run by the maintainer.
- **Load and switches.** About 2,000 Python starts, 30–60 minutes. It runs alone, after the last T2; stop on "stop". It records `LongPathsEnabled`, Defender real-time protection on/off (a scanner holding a handle moves the timings), the Python version and the file system.
