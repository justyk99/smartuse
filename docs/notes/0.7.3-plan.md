### F1 · two Stop hooks at once still leave one ledger line (lane A · half a day, plus the rounds) — the must-have
- **Evidence.**
  - `on_stop` claims `pending.json` by renaming it to `pending.<pid>.claimed` (`ledger.py:309–313`). Any failed read of the claimed file deletes it and returns (`:314–318`).
  - Traced in 0.7.2 E1 (`0.7.2-plan.md:265`): hook B still holds the file open for its own rename when hook A's rename wins. A's read fails with a sharing violation (`PermissionError`, errno 13). A deletes the claimed file. B's rename then fails on a deleted file (winerror 5). Nobody writes.
  - Measured: 4 rounds in 1,000 (2026-11-24) and 3 in 1,000 (2026-11-25) left no line, none left two. A held delete handle reproduces it every time (0.7.2 E1b).
  - `ledger-test.sh:52` is a known flake (`paid-guard-next-brief.md:34`): the same race.
  - The 0.7.2 scripts lived in a session scratchpad and are not in the repo.
- **Fix (the ROADMAP shape, `docs/ROADMAP.md:107`).** The read retries a `PermissionError` 5 times, 20 ms apart, the shape `write_json` already has (`ledger.py:175–181`). The claimed file is deleted only when its content is bad. Sketch (the builder proves it with the cases below):
  ```python
  p = MISSING = object()
  for attempt in range(5):
      try:
          p = json.loads(claimed.read_text(encoding="utf-8")); break
      except FileNotFoundError: return          # the other hook's rename took the file: that hook writes the line
      except PermissionError:                   # still open for the other hook's rename (Windows): wait, as write_json does
          if attempt < 4: time.sleep(0.02)
      except ValueError:                        # bad JSON or bad bytes: as today
          claimed.unlink(missing_ok=True); return
  if p is MISSING: return                       # D-YK24: not readable after 5 tries: the file stays, nothing is deleted
  ```
  - Why one line and never two: a hook writes only after it read the file under its own claimed name. While another hook holds a rename handle, that read fails. Once the handle is gone the file has one name, so one owner. The dedupe (`:361–368`) stays as the second guard.

  3. A `pending.json` holding broken JSON still disappears at Stop and leaves no line, as today.
- **Unit (red first; the builder writes these in `ledger-test.sh` before touching `ledger.py`).** The suite stops at its first FAIL (`ledger-test.sh:7`), so each new case is shown red on its own.
  - L1, Windows: a helper holds `pending.json` open with delete access and full sharing (stdlib `ctypes`, `CreateFileW`), as a rename in progress does. It lets go about 10 ms after it sees a `pending.*.claimed` name appear. One Stop event runs meanwhile. Wanted: one line for the task, no `pending.json`, no claimed file left (red: no line). Elsewhere it prints `SKIP <label>: Windows only`.

### F3 · the scan frames git's output on newlines only (lane B · 2 to 3 hours) — `docs/STATUS.md:15`, first item
- **Evidence.**
  - History splits git's whole output with `bytes.splitlines` (`scripts/term-scan.py:213`), which also breaks at a bare carriage return. The tree does the same per file (`:167`).
  - History knows git's own lines by their first bytes: `commit ` is skipped and names the label (`:214–217`); `ident ` is read for private patterns only (`:218–221`); `diff --git ` turns header mode on (`:222–224`), where `+++ `, `--- ` and `index ` lines are skipped (`:230–231`); `Binary files … differ` is skipped and counted (`:232–234`).
  - Git ends its lines with a newline. A bare carriage return inside a file line or a commit message stays inside that line (the message is indented after a newline only, `:207`). So the text after it starts a "line" with no prefix and can pass for one of git's own:
    - `x<CR>commit <term> …` is skipped whole;
    - `x<CR>Binary files <term> differ` is skipped and counted as binary;
    - `x<CR>diff --git a b` turns header mode on inside a hunk, so a following added line `++ <term>` is skipped (the r13 case, `term-scan-test.sh:99–106`, opened again);
    - `x<CR>ident <text>` loses its generic patterns.
  - The tree has no such lines, so nothing is skipped there. The miss is history only: a file since deleted or changed, or a commit message.
- **Fix.** History splits on the newline byte only and drops one trailing carriage return (CRLF text reads as today). Git's own lines are recognised on whole newline lines. A content line is then scanned in its carriage-return pieces, as today, so counts and excerpts do not move for text without a bare carriage return. The label's number counts newline lines. The tree keeps `:167`.
- **Acceptance (the user does).**
  1. The maintainer types `python scripts/term-scan.py --history --max-hits 1000000`, bare: `(0 private)`, and the same hit counts as the 0.7.2 code gives on the same commit.
  2. A private term after a bare carriage return and the word `commit`, in a file since deleted, is reported as `history@<hash>` under `private#1`. The term never appears in the output.
- **Unit (red first, `scripts/term-scan-test.sh`, temp repos, invented terms, each temp repo sets `core.autocrlf` to false).**
  - c1: a file line `x<CR>commit zebrafish and more`, committed, then removed: a `history@` private hit (red: 0 private).
  - c2: the same text in a commit message body, if git keeps a bare carriage return there (the builder checks the bytes first; if not, the case is dropped and §10 says so).
  - c3: a file with the lines `x<CR>diff --git a b` and `++ zebrafish`: one `history@` hit for the added line (red: none).
  - c4: `x<CR>Binary files zebrafish differ` in a file since removed: a history hit, and no `binary diffs not read` clause (red: skipped and counted).
  - c5 (pin): a CRLF file holding the term: the same tree label and the same history hit as before the fix.
  - c6 (pin): a file with carriage returns only, the term in its third piece: the tree label keeps `:3`.
  - The cases now in the suite stay unchanged (`:12–34`, `:45–106`), and the term is in no output.
- **Integration.** The script over this repo's whole history with the old and the new code on the same commit, plain `python`, no variables. Private must be 0 in both. The hit totals must be equal, or the difference is listed by pattern name only. **A private hit stops the step**: the builder reports the pattern number and the label, never the text; the maintainer decides.
- **Interactive.** The publish command of `CLAUDE.md:8`, typed as written on the laptop. Then a scratch repo holding c1's line in a deleted file: reported, starred.
- **Must not change.**
  - Exit codes (`:259`), the patterns (`:17–27`), `load_private` and the terms file format (`:32–46`), the options (`:184–187`), the summary line's shape (`:245`).
  - `star`, `mask`, `readings`, the one-hit-per-pattern rule (`:86–162`); private hits never capped (`:136–143`); the git command and its format (`:207–208`); the tree's reading (`:167`); the CI step (`ci.yml:55`).

## 9. Risks
- **F1 adds a wait.** A claimed file that stays unreadable costs about 100 ms once at that Stop. The ledger hook's limit is 20 s (`hooks.json:52–53`).
- **L1 depends on timing.** The helper lets go about 10 ms after the claim; the retries span 80 ms or more. On a loaded laptop the gap can shrink. If it flakes, widen the helper's side; never loosen what the case asserts.
- **Two lines instead of none.** Argued impossible in F1 (the name decides the owner), with the dedupe as the second guard. The rounds count doubles as well as drops; one double stops the feature.
- **Windows-only proof.** h4 and §39f need Windows and `LongPathsEnabled` = 0. Whether CI's Windows runner has the switch on is not known, so the laptop may be their only proof. h1 to h3 run everywhere.
- **§39f may be red before any change.** Then the paid check does not refuse at 240 characters and `SECURITY.md:46` is wrong today. The step stops and reports.
- **E1 makes folders longer than Windows tools like.** A failed cleanup leaves a folder in the temp area; it is listed, not forced.
- **F3 can move generic hit counts** on this repo if its history holds bare carriage returns. Old and new are compared on one commit; the publish rule stays 0 private.
- **F3's fixtures depend on git's line-ending setting.** The temp repos turn `core.autocrlf` off.
- **Laptop time and memory.** One T2 (about an hour), the rounds (30 to 60 minutes), E1 (under 30 minutes). Claude Code has stopped suites on low memory before; restart only on the maintainer's word.
- **Interactive runs set `HOME` to a scratch folder** (assumed to reach the hooks on Windows, as in 0.7.1 and 0.7.2; a leftover state folder is listed for the maintainer if not).
