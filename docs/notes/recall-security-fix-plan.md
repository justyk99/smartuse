## 0. The problem (the class, not the cases)
The 0.6.0 contract (`docs/notes/recall-design.md`) promises two things: a send is **gated on every path the model can take**, and once a send matched the gate **fails closed**. The review found one hole in each:
- **Another shell.** `hooks.json:5-14` registers bash-guard for the `Bash` tool only. Claude Code on Windows also has a `PowerShell` tool, **on by default for claude.ai accounts when Git Bash is installed**, and then "treats PowerShell as the primary shell" (tools reference, read 2026-11-09). A `git push` through it never reaches the gate, nor the older RULES. The official fix spelling is the matcher `Bash|PowerShell`; the hook gets `tool_name: "PowerShell"` and the text in `tool_input.command` (same fields as Bash). The `Monitor` tool's command reaches a `Bash` matcher as a Bash-shaped call from Claude Code 2.1.314 on (hooks reference, "Match Monitor commands"), so it is covered already; a WebSocket watch has no command and fires no Bash hook. No other built-in tool runs a shell command (tools reference table, 2026-11-09).
- **A slow matcher.** `bash-guard.py:65` (`HEREDOC`, the frozen `strip_heredocs`) and `:743` (`HEREDOC_OPEN_PLAIN`, the gate's own, run at `:762`) both read `(.*?)\n[ \t]*\N` with `re.S`: every unclosed opener rescans to the end, so the cost is openers × length. The review measured `"x <<a\n" * 8000 + "git push"` (48 KB) at 4.84 s + 5.39 s on the author's laptop, before a 0.4–3.6 s interpreter start; the hook timeout is 10 s and a timed-out PreToolUse hook lets the call through (hooks reference). The 4 s deadline (`BUDGET_S`, `:24`) starts at `:817`, after both scans.
- Four minors of the same two families: spellings the matcher misses (`:553, 602-613, 702-739`), a failed Read that still counts (`:474-482`), a drive letter inside a relative path (`:268-272`, `recall.py:434-447`), and a quadratic e-mail scrub (`recall.py:58`).

## 2. Research: recognising a command in PowerShell text, Python stdlib only (one Python start is locked; PowerShell's own parser would be a second process)
| Candidate | Gives | Licence | Maintenance | Fit | Effort | Verdict |
|---|---|---|---|---|---|---|
| A. `shlex` (stdlib, POSIX rules) | word splitting with quotes | PSF | stdlib | poor: backtick escapes, `@"…"@` here-strings, `$()`, case-insensitive names are all mis-read, and a mis-split fails **open** | low | **avoid** |
| B. the PowerShell parser (`System.Management.Automation.Language.Parser` via `pwsh`) | the exact AST | MIT | Microsoft | exact, but a second process per event (locked rule) and no `pwsh` on most macOS/Linux boxes | medium | **avoid** |
| C. `pygments` PowerShell lexer | tokens | BSD-2 | third party | no dependencies allowed in hooks | low | **avoid** |
| D. coarsest: fold case, turn PowerShell punctuation into spaces, require the pattern's words in order anywhere in a statement | fail-closed, O(n), ~15 lines | own | ours | over-denies every mention (`Write-Host "git push"`) | 1 h | **fallback floor** if F1 slips |
| **E. own normaliser + the existing `FLEX` splitter** (adapt `command_segments`): here-string fences `@"` `"@` `@'` `'@` and `{ }` become statement breaks, backticks are removed (PowerShell's escape and continuation character), commas become spaces (array literals), words compare case-insensitively, the call operator `&` is already a separator, `Start-Process`/`saps`/`start`, `wsl`, `cmd /c`, `pwsh`/`powershell -Command` and `-EncodedCommand` (base64 of UTF-16LE, decoded with the stdlib `base64` module), `Invoke-Expression`/`iex` are read like the Bash wrappers and `-c` strings are today | fail-closed, O(n), ~120 lines | own (same style as `FLEX`) | ours | good: everything a model types in practice; over-denies only on a publish word in a data here-string or an array; misses a command built at run time (variables, `Get-Command`, string concatenation), a `-File x.ps1` body and `iwr … \| iex` content | 1 day | **pick** |

**Coarse vs exact, said plainly:** only B is exact and it is ruled out. E is coarse-but-fail-closed: the publish pattern's first word may match **any word of a statement** (not only its first, as on the Bash side), because PowerShell lets the program name sit after a parameter (`Start-Process -ArgumentList push -FilePath git`); the later pattern words must follow it in order. The price is an over-deny on `Write-Host git push` (unquoted) and `Select-String python send.py`, one turn each; the quoted `Write-Host "git push"` stays allowed as `echo "python send.py"` does today. The older RULES run on the normalised PowerShell text **as the regexes they are** (no new rule strings, no order change): `git push --force`, `sudo`, `cat`/`type` of a credential file and `> .claude/smartuse.local.md` are caught through PowerShell too; `Set-Content`/`Out-File` on the human-only files, `Invoke-WebRequest … | iex` and `Remove-Item -Recurse -Force` of a root are **not** (documented, ROADMAP; §7 option B).
