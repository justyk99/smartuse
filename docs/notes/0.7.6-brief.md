## Carry-over rules
- One heavy job at a time on the laptop, at low priority (the maintainer may be gaming); suites never side by side; never `all.sh` there. The way to lower the priority is named by the orchestrator in each builder brief. Claude Code stops a background suite when memory runs low: report it, restart only on the maintainer's word.
- Any deny ends that action: a guard, a refused permission, a hook. Do not retry it, rephrase it or move it into a script file; report it. In E1 a refusal of a probe is the result.
- Builder briefs: every "as today" claim gets a file:line the builder has read; a bug gets its red case first; a check that is green on the base is shown red by a mutation. Name the import allowlists (wait-gate, recall, paid-guard, fresh-gate, and the eight-file check in heartbeat). No feature adds an import.
- The real Claude Code settings are never loaded and never written. A headless run passes `--setting-sources project`, `--permission-mode default`, `--no-session-persistence`, a `--plugin-dir` copy and a temp `HOME` for the hooks; it removes `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT` and `CLAUDE_PROJECT_DIR` from its environment, as `bench/ab.sh` does. No command names a settings file.
- E1a comes before everything: the version, the mode (`default`), one smartuse loaded from the copy, and where the state landed. Then the two controls. A harness that cannot tell "allowed" from "not allowed" proves nothing.
- A skill is typed in a headless run (`-p "/smartuse:<name>"`). A model-invoked run needs `--allowedTools Skill`.
- A launcher rule names the launcher, one hook script and one option word, each path by `${CLAUDE_PLUGIN_ROOT}`. Never the launcher alone: `py.sh` passes `-c` on. The rule is copied from the command, quotes included.
- No skill is granted `--recompute`, `until-done.py --trust`, `-c`, or heartbeat's `--json` and `--statusline`.
- Part A edits no `!` line and no command text. Every other entry of an `allowed-tools` line keeps its text; make-prompt's `Bash(git *)` stays (D-YK47).
- A result names its switches (the Claude Code version, the OS build, the Git Bash version, the permission mode, the settings sources, the model). What was not measured is written "assumed". A count never becomes a number in code.
- `--report` and `--receipts` keep their output byte for byte; each gets its pin before `ledger.py` is edited. `--view` writes nothing, makes no folder, joins a ledger line to its steps by the archive's file name only, and prints `steps: not kept` when there is none.
- The ledger is read as anyone's data: a bad line is skipped and counted, a printed field is cleaned of control characters and cut at today's caps.
- `fit_key` is one text in six hooks, `long_form` and `counter_in` one text in two; none moves. `ledger.py`'s import line does not move.
- New rules in a skill's grant get a security review round before T3 (R1). Release text states classes and what was measured, with the machine and the Claude Code version.
- Tests use a temp `HOME`. The private terms file and `.claude/*.local.md` are never read or printed; `.agents/` and `.codex/` are never touched. Builders stage files by name. No personal path, user name or real task name goes into a plan, a test, a doc or a committed mock.
- Each release needs T3 (both validates, the interactive scenarios on the merged branch, a fresh review and a security review), the bare publish scan showing `(0 private)`, and CI green on the pushed work branch before main moves. The version goes in both manifests, the CHANGELOG, the badge and the docs in the last feature (F2, V3).
