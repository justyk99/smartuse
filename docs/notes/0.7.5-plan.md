# smartuse 0.7.5 — Python starts isolated (plan, 2026-11-27)

Base: the 0.7.4 release commit. It is not cut yet at planning time: `fix-0.7.4` is at `8021af1`, public main at `2259947`, and 0.7.4's docs step and T3 are still open. Line numbers below are of the working tree of `fix-0.7.4`, read 2026-11-27; the builder re-checks each one before editing.
Work branch (proposed): `fix-0.7.5` from that commit; every feature merged `--no-ff`. One experiment, five features, one security round; each feature one day or less.

## 1. Brief
- **What the owner gets.** Every hook starts Python the same way on every machine: no `PYTHON*` variable, no user site folder, no site folder of the interpreter, no working folder and no hooks folder on the import path. A stray `PYTHONPATH` or `PYTHONHOME` can no longer replace a module in every hook or switch every hook off. `/smartuse:doctor` says how Python started. `SECURITY.md` says what this closes and what it cannot.
- **Why this scope.** It is item 1 of "To 1.0, in order" (the 0.7.4 plan §2b, D-YK34) and the first half of `docs/ROADMAP.md:36`. The 1.0 bar says the hooks never block a turn by mistake; today the hook's environment decides whether they run at all.
- **What happens today, by trace (E1 measures it).**
  - `py.sh` passes the session's environment to Python untouched and adds `PYTHONUTF8=1` (`py.sh:22`). Nothing is ignored.
  - A folder on `PYTHONPATH` comes before the standard library. A `json.py` in it is imported by all seven hooks (`bash-guard.py:43`, `file-guard.py:25`, `heartbeat.py:68`, `ledger.py:67`, `recall.py:42`, `until-done.py:40`, `wait-gate.py:73`).
  - A failed import happens before `main()`, so Strict's "an error denies" (`bash-guard.py:3426–3431`) never runs: Python exits 1, which Claude Code treats as a non-blocking error, and the call goes through at both levels.
  - A wrong `PYTHONHOME` stops Python at start: the probe fails for every candidate (`py.sh:49–58`) and the launcher exits 0 in silence (`py.sh:65`), or the remembered name is run and dies (`py.sh:45`).
  - The hook's environment is the session's (the hooks reference: "a hook process inherits the parent environment"). It comes from the user's shell, and from a settings file's `env` block, which `file-guard` compares only for the plugin's own option names (`file-guard.py:53–58`).
- **Maintainer steps: one.** The word for the two pushes (D-YK39), after T3. Plan approval is under the standing go to 1.0.
- **Version.** 0.7.5: a changed start line, test honesty and docs. No new rule, gate, adapter key or option. The launcher is the one file every hook passes through, so it has its own security round (R1).
- **Cut line.** F1 and F2 ship together or not at all: flags without the new remembered-name mark leave an upgraded machine with no second try. If the batch runs long, F4 moves out first, then F3 (STATUS then carries "the code-page cases no longer bite through the launcher").

## 2. Not in this (said once)
- **The plugin's own files and the interpreter's own files.** `hooks.json`, `py.sh`, the hook files, their compiled copies in `hooks/__pycache__/`, the Python program and its standard library belong to the user's account. A hook runs as that account and cannot protect them from it. F5 says so by class; no guard is built (§2b, D-YK38).
- **Which Python runs.** `PATH`, a venv and the `py` launcher's own settings pick the interpreter. Isolation changes how it starts, not which one it is.
- **A new proof for a remembered name** (`docs/ROADMAP.md:35`, second half) and trusting a real `WindowsApps` alias (first half): unchanged. One corner gets worse and is said in §9 (D-YK42).
- **`hooks.json`.** No flag goes into its 19 commands. The flags live in `py.sh` only.
- **Any hook's logic.** No rule, no reason text, no state file. `fit_key` (six copies), `long_form` and `counter_in` (two copies) do not move.
- **What a hook hands on.** `until-done`'s `check:` child (`until-done.py:263`) and `watch.py`'s git calls (`watch.py:248–250`) keep the session's environment, `PYTHONUTF8=1` included (D-YK40).
- **A version check in the probe.** A Python older than 3.9 still reaches the hook as today; doctor's line says FAIL for it (`heartbeat.py:708–709`).
- **A switch for isolation.** No plugin option, no variable.
- **Start speed as a goal** (`docs/ROADMAP.md:53`). E1 reports what `-S` saves; nothing is tuned for it.
- **The skills' grants** (`Bash(bash *)`, reply-style's `Bash(python3 *)`): 0.7.6. **The guard batch:** 0.7.7.

## 2b. What "an install the model can write" means
A hook is a program the user's account runs. Whatever that account may write, a command Claude runs may write.

| What can change the code a hook runs | Where it lives | 0.7.5 |
|---|---|---|
| A `PYTHON*` variable in the hook's environment | the user's shell profile; a settings file's `env` block | closed: ignored (`-I`) |
| The user site folder (`usercustomize`, a `.pth` line) | under the home folder, no admin needed | closed (`-I`) |
| The working folder as an import folder | the user's project | closed for hook scripts since 0.7.0 (`py.sh:32–34`); now for every start |
| A new file beside the hooks | the plugin's `hooks/` folder | closed (`-I`): that folder is no longer an import folder |
| The interpreter's site folder (a `.pth` line, `sitecustomize`) | inside the Python install or a venv; any `pip install` writes there | closed with `-S` (D-YK36) |
| The plugin's files: `hooks.json`, `py.sh`, the hook files, their compiled copies | the plugin folder | **open: stated by class** |
| The interpreter's own files | the Python install (a per-user install is user-writable) | **open: stated** |
| Which interpreter is found | `PATH`, a venv, the `py` launcher's settings | **open: stated** |
| The remembered-name file | `~/.claude/smartuse/interpreter`, human-only in both guards by name (`bash-guard.py:91`, `:133`; `file-guard.py:26`) | it still cannot name a command; from F2 it cannot pick the start mode either |

Only something outside the user's account can close the three open rows: an install owned by another account, or Claude Code's own permission rules and sandbox, which run before any hook. A guard for the hook files would be new patterns in two always-on rules, and it would refuse a plugin developer's own edits when a checkout is loaded as the plugin. That is a candidate for the guard batch, not for this release.

## 3. Rules for every feature
- Frozen: `RULE_NAMES` (`bash-guard.py:162`), `GATE_NAMES` (`:167`), `FLOOR` (`:171`), `KNOWN_RULES` (`heartbeat.py:79`), `hooks/hooks.json`, `all.sh` NAMES (`all.sh:20`), `ci.yml` steps, `fit_key` in six hooks, `long_form` and `counter_in` in two. A builder who finds one must change stops and asks.
- Never touched: `.claude/*.local.md`, the private terms file (never read, never printed), `.agents/`, `.codex/`. Stage by file name. Test terms and paths are invented.
- A bug gets its failing case first, shown red on the base commit, then the fix. Every "as today" claim in a builder brief carries a file:line the builder has read.
- **Every Python start of the plugin goes through `py.sh`.** The flags live there and nowhere else. `hooks.json`, `settings.json:4` and the skills' `!` lines are not edited.
- **The loader line `LDR` (`py.sh:36`) stays byte for byte.** Under `-I` Python adds no entry of its own to `sys.path`, so the loader leaves the path alone, as its comment already says for `PYTHONSAFEPATH` (`py.sh:34`). In the second try (F2) it replaces `''` as today.
- **The remembered-name file picks a probe step to skip.** Never a command (0.5.1), and never the start mode (new): no content of that file may select the un-isolated start.
- **`-P` is never passed.** Python 3.9 and 3.10 do not know it, and `-I` already drops that path entry on every supported version.
- Import allowlists (four suites have one): `wait-gate-test.sh:983`, `recall-test.sh:218`, `paid-guard-test.sh:80–81`, `fresh-gate-test.sh:1174`. No feature adds an import. F4 reads `sys.flags`, and `sys` is already imported (`heartbeat.py:68`).
- An unknown is never a number in code. E1's numbers go into §10 and the release notes. `py.sh` gains no timeout, count or threshold.
- A result names its switches: the OS build, the Git Bash version, each interpreter's version and where it came from, and whether a venv was active. A result is claimed for those only; every other build is "assumed" and covered by F2's second try.
- Plants go in temp folders only. Never in the real home, the real hooks folder, the real user site or an interpreter's site folder. A temp `HOME` does not move Python's user site on Windows, so a user-site plant goes through `PYTHONUSERBASE`.
- An event with a Windows path in it is written to a file and piped from there, never typed into a `printf`. An empty answer is trusted only after a known-deny event went through the same pipe.
- `py.sh` stays bash 3.2 safe (`heartbeat-test.sh:728`). The laptop's bash is newer, so only CI's macOS job proves it.
- One heavy job at a time on the laptop, across all builders, at low priority; suites one at a time; never `all.sh` there. Claude Code stops a background suite when memory runs low: report it, restart only on the maintainer's word.
- After a merge's automated security review: classify each finding against the class list of `SECURITY.md` first; one fix round, then report.

### F1 · every hook starts isolated (lane A, after E1 · three quarters of a day) — the must-have
- **Evidence.**

- **Fix** (`py.sh` only; the comment block is rewritten in the same voice).

  export PYTHONUTF8=1     # kept: a hook's child process inherits it, as before
  ISO="-I -S -X utf8"; [ -n "${PYTHONDONTWRITEBYTECODE:-}" ] && ISO="$ISO -B"
  …  exec $P $ISO "$@"                      # :45, the remembered name
  …  P=$($cand $ISO -c "import sys; …")     # :51, the probe proves the start the hook will get
  …  exec "$P" $ISO "$@"                    # :55
  …  exec $cand $ISO "$@"                   # :57

### F2 · the remembered name is proven isolated; a Python that cannot start isolated still runs the hooks (lane A, after F1 · half a day)
- **Evidence.**
  - The remembered name is run without a probe (`py.sh:41–45`): that is its purpose (0.5.1, `docs/notes/py-cache-fix-plan.md` §2, design D).
  - Every machine upgrading from 0.7.4 holds a bare name there, written by a probe that had no flags (`py.sh:54`). With F1 alone that name is run with the flags, unproven, for ever.
  - A Python that needs `PYTHONHOME` to find its library, or a `python` that refuses `-I`, works today. With F1 alone it has no hook at all.
  - Python exits 2 on an option it does not know, and exit 2 blocks a PreToolUse call, keeps a Stop from ending and blocks a prompt (the hooks reference). A flag must never reach an interpreter that was not proven with it in this start or marked as proven.
- **Fix** (`py.sh`).
  ```bash
  case "$P" in "python3 -I"|"python -I"|"py -3 -I") P=${P% -I}; W=${P%% *} …   # :41: a bare name is probed again
  printf '%s -I\n' "$cand" > "$C"                                             # :54: remembered with its mark
  # after the loop, before :59 — no candidate started isolated: the 0.7.4 start
  for cand in "python3" "python" "py -3"; do
    <resolve $cand's first word as :42–44 do; skip a WindowsApps hit>
    P=$($cand -c "import sys; …" </dev/null 2>/dev/null) || continue
    <exec "$P" "$@", or exec $cand "$@", as :53–57 without $ISO; write nothing>
  done
  ```
  - The file holds one of three exact words, each a name and the mark ` -I`. At most 10 characters, inside the 16 the launcher reads (`:39`).
  - A bare name, a path or anything else is probed again and rewritten. So is the new word on a downgrade to 0.7.4.
  - The second try is today's start. It is reached only when all three candidates failed the isolated probe in this very run. It is never remembered, so the file cannot choose it.
  - A `WindowsApps` hit gets no second try: the Store stub is started once per event, as today.
- **Acceptance (the user does).**

  3. A machine with no Python reads the same sentence at session start as today, and its tool calls keep working.

### F3 · the code-page cases keep biting (lane B, after F2 · half a day, tests only)

## 9. Risks
- **Every hook dead on a machine nobody tested.** The answer is in four layers: the probe carries the flags; a Python that fails it gets the second try; E1's stop rule; CI's five jobs before main moves. What is left is a Python that passes the probe and then fails an import that `-S` hides: none is known, and the hooks import the standard library only (s1).
- **A remembered name whose target changed.** If `PATH` later gives a marked name to a Python older than 3.4, it refuses `-I` and exits 2: a guarded call is blocked and a Stop is kept from ending. Before 0.7.5 that Python ran the hook and died with exit 1. A Python older than 3.4 does not run the hooks at all, so the corner is narrow; it is said in the ROADMAP and not fixed here (D-YK42). The launcher already hands on Python's own exit code when a hook file is missing (`heartbeat-test.sh:672–675`), so this is the same kind of failure, not a new one.
- **A second try on every event.** A machine that needs it probes up to three times, then starts plain: several starts per event, never remembered. Slow but correct, and a hook that times out lets the call through.
- **Two smartuse versions on one machine** (an installed 0.7.4 beside a 0.7.5 checkout) rewrite each other's word, so both probe on every event.
- **Pinned texts move.** Three bytecode cases and six cache-word cases change what they expect. Each is shown red first and changed in the same commit as its code.
- **Tests that stop biting.** Any case that sets a `PYTHON*` variable in front of the launcher is now blind. The grep found only the code-page cases (F3) and `PYTHONDONTWRITEBYTECODE` (carried). A later one would be the same trap; `CONTRIBUTING.md` gets no rule for it yet.
- **Users who relied on a variable.** `PYTHONIOENCODING` no longer changes a hook's output, and `PYTHONPYCACHEPREFIX` no longer moves the hooks' bytecode. Both are in the CHANGELOG under "Changed".
- **Windows-only numbers.** E1's times are the laptop's. Linux and macOS get one `INFO` line per CI job (t0), nothing more.
- **Not on the laptop.** A real Store Python, the install manager's aliases, `py` with its own settings file. The `WindowsApps` rule is unchanged, so those users keep two starts per event, now both isolated.
- **bash 3.2.** The laptop cannot prove it; CI's macOS job does, which is one more reason for D-YK39.
- **The venv case.** Where a venv cannot be made it prints `SKIP`; `no_site` 1 in i4 still proves the site folder is not read.
- **Timing under a game.** E1e interleaves its rounds; a result inside the spread is reported as "no measurable change", never as a gain.
- **Laptop time.** E1 (under 40 minutes), `heartbeat-test.sh` about six times (two to three minutes each), the six fast suites twice (about 8 minutes each time), one T2 (about 45). Claude Code has stopped suites on low memory before; restart only on the maintainer's word.
- **Over-claiming.** "Isolated" is Python's word for one start mode. F5 uses it only with the list of what stays open beside it.
