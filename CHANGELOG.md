# Changelog

## 0.7.7 — 2026-11-27, "one view of a run"
`/smartuse:ledger` now prints the runs and, under the table, the steps of each run-plan run, so one command answers "what did that run cost, and what did each step do". No new rule, gate, adapter key or option; `hooks.json`, `py.sh`, `RULE_NAMES`, every hook's logic and what a ledger line holds are unchanged. Plan: `docs/notes/0.7.6-plan.md` (Part B).
- **The view** (V1, `ledger.py --view`). One command prints `--report`'s table (the last N runs, then the medians by skill and mode), then, for each run-plan run shown, the same block `--receipts` prints for it: one row per plan step, then the closing line with each model's share of agent output. The look is look B, the maintainer's choice on 2026-11-27 from two looks rendered from the repo's example run (the laptop had no ledger of its own). Each run's steps come from that run's own archive (`runs/<started_at>_<task>.json` in its project's state folder), never from the nearest run. A run still in progress comes last, under `running now`, when this project's `routing.json` is active. The table and the step blocks are printed by the same code `--report` and `--receipts` use, so the commands cannot disagree on a number.
- **The words it takes** (V1, V2). `/smartuse:ledger` alone shows the last 10 runs. `N` shows the last N runs, a task word shows every run of the tasks holding it, `all` shows every run. The skill's `argument-hint` and text say so, and its grant names `ledger.py --view *` where it named `--report *`.
- **`steps: not kept`.** A run-plan run whose archive is gone (an older run, or one cleaned away) prints `steps: not kept (<archive file name>)` under the table. Nothing is filled in from another run.
- **A bad ledger line is counted, not fatal** (V1, for `--view`). A line that is not a JSON object, or has a field that cannot be printed, is left out and counted (`1 line unreadable`, `2 lines unreadable`); the other runs print and the exit code is 0. A printed field (and a key inside a run) has its control characters turned into spaces and is cut short: task names at 40 characters, project, skill, mode and self-check at 80, text inside a run at 200 (the view's own caps; `--report` cuts only task names). A number too large to print is counted as unreadable. `--report` is unchanged and still ends with a traceback on a bad line (on the ROADMAP).
- **Reads only.** `--view` writes nothing and makes no folder. For a run-plan line it reads that line's own project's `runs/` folder under `~/.claude/smartuse/`, so it covers every project in the ledger, as `--report` lists every project. The folder is the one the key rule gives for the line's `project_path`; a `project_path` that is empty, relative, holds `..`, or names a network share or device path (`\\server\…`, `\\?\…`) is never opened and prints `steps: not kept`. The README and `SECURITY.md` say so.
- **What did not change.** `--report` and `--receipts` (and `--receipts --json`) print what they printed in 0.7.6, byte for byte (pinned by a test added before the change). `/smartuse:receipts` is as it was and stays the command for one run alone. An empty or missing ledger prints the same two lines as before. The planned pointer sentence in `/smartuse:receipts` was not added. `--view --json` was planned as the first thing to drop if the day ran short, and was not built.
- **The checks.** `ledger-test.sh`, new cases red on 0.7.6 first: the golden text of look B from the repo's own example run; that run's six step lines and its closing line; a run whose archive is gone; a second run of the same task not shown under the first; a ledger with a half line, a list line and a line with no `task`; a 300-character task name with an escape character and a newline in it; `N`, a task word and `all`; an empty and a missing ledger; an active `routing.json` with no ledger line yet; no file changed under a temporary `HOME` and no folder made; a `project_path` that is empty, relative, holds `..` or names a folder that is gone; and the skill's own `!` line run through the launcher. `heartbeat-test.sh` g3 and g4 fail when the skill's `!` line runs `--view` and its grant still says `--report`, and pass with both moved.
- **Live check** (Claude Code 2.1.332, permission mode `default`). `/smartuse:ledger` printed the table, then the run's steps, on the repo's example run.
- **Changed.**
  - `/smartuse:ledger` prints the table and each run-plan run's steps; in 0.7.6 it printed the table alone. `/smartuse:ledger <task>` shows that task's runs with their steps.
  - Its grant names `ledger.py --view *`, no longer `--report *`. The same command in another spelling asks, as in 0.7.6.
  - `ledger.py --report` is kept for scripts and prints what it printed.
- **What is not covered.** The live check ran on one machine: the author's Windows 11 laptop, Claude Code 2.1.332, mode `default`. Linux and macOS (until CI), any other Claude Code version (2.1.300 among them) and any other permission mode are assumed; CI starts no Claude session, so the laptop's live check is the only proof of the skill line. Listed in `docs/STATUS.md`.

Fixed: keys inside a run were printed without cleaning (an escape code or newline in a model name printed raw), one bad record (a huge number, a lone surrogate) emptied the whole view, and a `project_path` naming a network share made the view reach for it; each has a test, red first.

## 0.7.6 — 2026-11-27, "the skills ask for less"
No skill pre-approves "any bash command" or "any python command" any more: each of the eight skills names the launcher commands it really runs, and the `git` and `svn` rules of make-prompt, living-docs and run-plan are cut to the exact commands their `!` lines run, or to forms whose tail is paths only. Also fixed: make-prompt aborted at load in default permission mode. No new rule, gate, adapter key or option; `hooks.json`, `py.sh`, `RULE_NAMES` and every hook's logic are unchanged. Plan: `docs/notes/0.7.6-plan.md`.
- **The skills ask for less** (F1). Seven skills carried `Bash(bash *)` and reply-style carried `Bash(python3 *)`. In the turn that invoked such a skill, every command that started `bash ` ran without a prompt, `bash -c "<any text>"` and the launcher with `-c "<any Python>"` included. Now no skill grants a whole shell or interpreter. Each launcher rule names three things: the launcher (`py.sh`), one hook script and one option, all by `${CLAUDE_PLUGIN_ROOT}`, for example `ledger.py --report *` for ledger, `heartbeat.py --line` for status, and for living-docs `ledger.py --state-dir --create` and `ledger.py --put pending.json *`. The line is written as a YAML list with one single-quoted rule per item. reply-style runs no Python, so its `Bash(python3 *)` is removed, not narrowed. A command a skill does not name goes back to the user's own settings: a prompt in default mode, a refusal headless without a permission flag. `--recompute`, `until-done.py --trust`, `-c` and heartbeat's `--json` are granted to no skill.
- **make-prompt's `git` is narrowed, and why** (R1 fix). `Bash(git *)` lets `git -c alias.x='!<command>' x` run any program with no prompt, so keeping it would have left the launcher claim half true. make-prompt now grants its `!` lines' exact commands (`git branch --show-current`, `git status --short`, `git log --oneline -6`, `svn info --show-item revision`, `svn status`) and `git log --format=%an -- *` for the owner lookup its text describes. A `git` or `svn` command outside them asks, `git config user.name` and `svn log` included.
- **The git and svn rules cannot take an option that writes or runs** (T3 fix). `git log`, `git diff` and `git show` take `--output=<path>`, which writes a file; `svn diff` takes `--diff-cmd` and `-x`, and the svn commands take `--config-option`, which can run a program. Each git and svn rule in the three skills is now exact, or ends in ` -- *` so its tail is paths. Three living-docs rules keep a free commit or revision id before any `--` (`git show --stat *`, `git show * -- *`, `svn diff -c *`): a model typing an option there is not stopped by the grant (named in `SECURITY.md`). Rules no skill used were dropped (living-docs' `git log`, `git diff`, `svn log`; run-plan's `git status`, `svn status`).
- **make-prompt loads in default permission mode again** (fixed bug). Claude Code 2.1.332 refuses a `{ …; }` group in a `!` line ("can't be checked before it runs"), so `/smartuse:make-prompt` aborted at load in default mode. 0.7.5 did too: the skill never reached Claude. Its four `!` lines are plain pipes now, the svn hint moved into the label, and `Bash(echo *)` was added for the existing `echo` fallbacks. The checks below fail on a brace group, `((`, `$(` or a subshell in any `!` line.
- **The checks** (`heartbeat-test.sh`, beside t1). A small reader takes `allowed-tools` in every spelling the skills page allows (one line with commas, spaces, a YAML list, quotes) and fails closed on an item it cannot read. g1: no skill grants a bare `Bash`, `Bash(*)` or a rule whose first word is a shell or interpreter (`bash sh zsh dash python python3 py node perl ruby pwsh powershell cmd env xargs eval exec`, `sh -c` and `env bash` forms included), `PowerShell(` too. g2: every rule that names `py.sh` or a hook script has the whole shape, never the launcher alone, never `-c`, `-`, `--recompute` or `until-done.py`. g3: every launcher command a skill's text starts is covered by a rule of that skill, matched as the permissions page says. g4: each skill's option words equal a table in the test, so a skill that gains one fails. g5: a `git` rule is a read form. g6: no brace group, `((`, `$(` or subshell in a `!` line. Each check was shown red on a copy first (m4 to m13: ledger turned back to `Bash(bash *)`, receipts' `!` line changed to `--recompute`, run-plan given a launcher-only rule, status given `--json`, and the spellings the first reader missed).

## 0.7.5 — 2026-11-27, "Python starts isolated"
Every hook now starts Python in its isolated mode wherever that Python accepts the flags, so no `PYTHON*` variable and no site folder changes how a hook starts (bash's own start-up settings and `PATH` still do), and doctor says how Python started. No new rule, gate, adapter key or option; `hooks.json`, `RULE_NAMES`, the floor and every hook's logic are unchanged (one line of `heartbeat.py`, doctor's Python line, moved). Plan: `docs/notes/0.7.5-plan.md`.
- **Hooks start isolated** (F1). `py.sh` starts every Python it runs (the remembered name, the probe, the proven path, the candidate itself) with `-I -S -X utf8`, except the second try below: no `PYTHON*` variable, no user site folder, no site folder of the interpreter (so no `.pth` line and no `sitecustomize`), and neither the working folder nor the hooks' folder on the import path. UTF-8 mode stays, by option, because `-I` ignores `PYTHONUTF8`; the variable is still exported, so a hook's child process (`until-done`'s `check:`) runs as before. `PYTHONDONTWRITEBYTECODE` is carried over as `-B`. The probe carries the flags too, so a Python that refuses one is skipped, as the Store stub is. A check reads every import in the eight hook files and fails on any name outside the standard library.
- **The remembered name is proven isolated, and a Python that cannot start that way still runs the hooks** (F2). `~/.claude/smartuse/interpreter` now holds `python3 -I`, `python -I` or `py -3 -I`; any other content (a 0.7.4 bare name included) is probed again and rewritten once. If no candidate starts isolated (it refuses a flag, or needs `PYTHONHOME` to find its library), the hooks start the 0.7.4 way, never remembered, and never on a `WindowsApps` hit. A flag never reaches a Python that was not proven with it in that run or marked as proven.
- **The code-page cases can fail again** (F3). Eight suites proved that a hook reads its event as bytes by setting `PYTHONIOENCODING=cp1252` in front of the launcher, which now ignores it, so each case would have passed with the proof gone. Each such case now starts the interpreter itself. A copy of `heartbeat.py` that reads text loses the event (`heartbeat-test.sh` m3); before the edit, every mutated hook passed the old case.
- **Doctor says how Python started** (F4). Its `python:` line ends `· isolated`, or `· not isolated (this Python did not start with -I -S: its PYTHON* variables and site folders are read; the hooks still run)`. Not a FAIL: the hooks are live.
- **Measured first** (E1, on the author's Windows 11 laptop, build 26300, Git Bash 5.3, one per-user Python 3.13 install; the laptop was in use). Every hook (the seven and `watch.py --file`) answered byte for byte the same under `-I -X utf8` and under `-I -S -X utf8` as under 0.7.4's start, so `-S` is kept. Through 0.7.4's launcher, a `PYTHONPATH` folder holding a `json.py` ran inside the guard and `sudo ls` was not denied, a `json.py` beside the hooks ran, a `usercustomize.py` and a `.pth` line under `PYTHONUSERBASE` ran, a wrong `PYTHONHOME` stopped every hook, and in a venv first on `PATH` a `sitecustomize.py` and a `.pth` line ran; under the isolated start none of them ran and the guard denied and allowed as before. `-I` alone left the venv's site folder open: only `-S` closed it. `py -3` hands the flags on. Cost: no measurable change (medians over 30 interleaved rounds: a bare Python start 40.4 ms with 0.7.4's start, 37.6 ms with `-I -X utf8`, 28.2 ms with `-I -S -X utf8`; one allow event through `py.sh` 150.0, 158.8 and 164.8 ms, measured on scratch copies of the launcher before the R1 fix; each difference is smaller than the spread).
- **Not measured.** Linux and macOS (until CI), bash 3.2, a real Store Python, the Python install manager's aliases, any Python other than 3.13 and any older than 3.9, and a quiet laptop. The README's speed table (method M) is not re-run and is unchanged.
- **Changed.**
  - `PYTHON*` variables no longer reach the hooks, `PYTHONIOENCODING` and `PYTHONPYCACHEPREFIX` included. `PYTHONDONTWRITEBYTECODE` still does (as `-B`).
  - The remembered-name file gets its mark and is rewritten once, on the first event after the update; nothing is deleted by hand. Going back to 0.7.4 reads the marked word as unknown, probes again and rewrites it.
  - A remembered name that `PATH` later hands to a Python that refuses `-I` (Python 2, or 3.3 and older) is probed again: the launcher sees the refusal before the event is read (assumed for a real Python 2 or 3.3; proven on stand-ins that refuse `-I`), and the event is still answered (R1; before the fix such a Python exited 2, which blocks a call, a prompt and a Stop). smartuse 0.7.4 in that layout ran the hooks off with exit 1 (by trace); 0.7.5 rewrites the file if another candidate starts isolated, and otherwise runs the second try.

A guard for the plugin's files is a candidate for the guard batch, not built here.

- **Security review** (of the code above, before release; plan `docs/notes/recall-security-fix-plan.md`). It found that the gate's two promises, "gated on every path" and "fails closed once a send matched", each had a hole. The batch went through ten review rounds; one fix round was reverted after its review found regressions. Early rounds found new crafted-command classes, several caused by the previous fix, so it ended with a different rule: a command the gate cannot read counts as a send while the sources are unopened. Fixed, each with tests that fail on the code before them:
  - **The closing rule: a command the gate cannot read counts as a send while the sources are unopened.** Classes: a very long command (over 32 KB), heredocs past the scan cap, three or more command substitutions, a `-c` / `eval` / `iex` / `cmd /c` / `-Command` string handed to another shell, and in PowerShell typographic quotes or dashes, escaped quotes, a block comment (`<#`), and `Start-Process` (or `start` / `saps`) as a standalone word anywhere in the command (its arguments are not read). With `publish:` listed and a source unopened (right after a compaction, or before the sources are first opened), a PowerShell command that holds the word `Start-Process`, `saps` or `start` anywhere is denied once until the sources are re-read, including `npm start`, a `$start` variable or the word inside a quoted string. A backtick escape inside that word is not caught yet (0.6.1). The reason names the class and says to open the sources or simplify. Once the sources are opened, such a command is read as before. It counts only when the adapter lists `publish:`. The cost is one turn for an unusual but harmless command right after a compaction. For a command over 4,096 characters the source check runs before the older rules.
  - **Another shell.** On Windows the PowerShell tool is on by default for claude.ai accounts, and it never reached bash-guard. The hook now runs for `Bash|PowerShell`; the older rules and the gate read the PowerShell text. The match is coarse: a publish word anywhere in a statement counts, so an unquoted `Write-Host git push` is an over-deny (one turn); a form it cannot read (typographic quotes or dashes, an escaped quote, a block comment, a `Start-Process` word) counts as a send while the sources are unopened. An adversarial PowerShell tokenisation pass is listed for 0.6.1. An encoded PowerShell command that does not decode is denied with its own reason; one that does is a string handed to another shell (counted as a send while the sources are unopened). `CLAUDE_CODE_USE_POWERSHELL_TOOL=0` turns the tool off. From Claude Code 2.1.314 (confirmed on 2.1.321), Monitor commands reach the same check.
  - **A slow command.** A crafted command could keep the heredoc scan busy past the hook's 10 s timeout, and a hook that times out lets the call through. The deadline now starts when the hook starts, and the heredoc scan has a bound on heredoc openers and delimiter length; past it the bodies are read as code (an over-deny) or, as a whole, as a command the gate cannot read. A 48 KB command that took 4.84 s + 5.39 s in the two scans is now denied in 0.31 s (median wall of 5 runs, interpreter start included; the maintainer's laptop, 2026-11-10).
  - **More spellings of a send** are read: wrappers and package runners, here-strings, `echo` or `printf` piped into a shell, git aliases, command names in any case, more shell names, a script name with a trailing dot or space.
  - **A failed Read is not an opened source.** A Read whose result is an error (a missing file, a denied Read) no longer counts; a Read whose result never arrived still does.
  - **A `:` inside a path part, or a part of only dots**, in a `sources:` or `handoff:` value is refused by its text, before any file call.
  - **recall's e-mail scrub** is linear in the length of the text, and a pasted blob is cut before it is scrubbed.
  - Not fixed, and said so: a command built at run time is not seen; the frozen older rules are slow on a very long, dense command (when the sources are opened or there is no adapter, such a command can outlast the hook timeout); a Python start slower than about 6 s is outside every deadline; some other ways of handing a command to another shell or interpreter are not yet recognised as such (other spellings of the same launchers, text fed on standard input, process substitution, shell functions and traps), and are listed for 0.6.1; the PowerShell side does not yet have the older rules for write verbs, download-then-run and script-file bodies. The limits are listed in the README and the contract; the rest is on the roadmap.

## 0.5.1 — 2026-10-25, "the launcher remembers a name, not a path"
- **The launcher's remembered interpreter is a name now.** In 0.5.0 `hooks/py.sh` ran the absolute path stored in `~/.claude/smartuse/interpreter`, an ordinary user-state file that neither guard listed: a writable state file chose the program every hook ran, in every repo (found by the push security review, 2026-10-25; plan `docs/notes/py-cache-fix-plan.md`). Anything else in the file (a path, another word), a name PATH no longer has or has only as a file that cannot run, or an alias under `WindowsApps` (any case) is ignored and probed again. The file is read up to 16 characters and written only into a regular file or a new one (never through a symlink, never a FIFO). A 0.5.0 cache (a path) is replaced by a name on the first event: nothing to delete by hand. The rule's known limits (ROADMAP) are unchanged; with a name-only cache, a write that gets past them can only pick among `python3`, `python` and `py -3` as PATH resolves them — it can no longer name a program.
- **bash-guard's destructive-SQL rule is linear.** It rescanned the rest of the command from every position, so its time grew with the square of the command's length: 16 KB of ordinary text took 12 s on the author's laptop. It is anchored now, with the same matches (rules are searched with `re.S`), and that command takes under a second.

Eight bypasses the old one-line regex allowed are caught (`/bin/bash`, a leading space, `then bash`, `source /dev/stdin`, `eval "$(cat)"`, a pipe after the body, a line continuation, `ssh host "bash -s"`). In exactly the state-write shape (`bash …/py.sh …/ledger.py --put|--unit|--run`, nothing else on the line), quoted arguments are data.
- Tests: `hooks/tests/all.sh` runs the five hook suites and `bench/tests/ab-test.sh` and ends with one line counted from the PASS lines: `run 126 · ledger 46 · until-done 36 · file-guard 10 · heartbeat 67 · ab 36` (the earlier "until-done 24" counted the `ALL PASS` line). Heartbeat cost stated as one figure everywhere: ~80 ms per event through the launcher.
