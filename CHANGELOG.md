# Changelog

## 0.5.1 — 2026-10-25, "the launcher remembers a name, not a path"
- **The launcher's remembered interpreter is a name now.** In 0.5.0 `hooks/py.sh` ran the absolute path stored in `~/.claude/smartuse/interpreter`, an ordinary user-state file that neither guard listed: a writable state file chose the program every hook ran, in every repo (found by the push security review, 2026-10-25; plan `docs/notes/py-cache-fix-plan.md`). The file may now hold only `python3`, `python` or `py -3`; `py.sh` looks that word up on PATH, exactly as its probe would, and runs it — builtins only, so still one Python start per event. Anything else in the file (a path, another word), a name PATH no longer has or has only as a file that cannot run, or an alias under `WindowsApps` (any case) is ignored and probed again. The file is read up to 16 characters and written only into a regular file or a new one (never through a symlink, never a FIFO). A 0.5.0 cache (a path) is replaced by a name on the first event: nothing to delete by hand. Users whose only Python is the Microsoft Store one or the Python install manager (3.14+, python.org's default; both put their commands under `WindowsApps`) keep 0.4.0 speed, two starts per event, because an alias is never trusted.
- **The file is human-only.** file-guard (Write / Edit / MultiEdit / NotebookEdit) and bash-guard's human-only rule (`>`, `tee`, `sed -i`, `cp`, `mv`, `python -c`, `py.sh`) cover `~/.claude/smartuse/interpreter`, including the spellings Windows maps to the same file (a trailing dot or space of any part, `::$DATA`); file-guard also matches the path the OS resolves (links, junctions, short 8.3 names of what exists; for at most 3 s, failing closed when it gives up) and denies a path under smartuse with a part of only dots and spaces (fail closed), with the reason "…or which Python runs the hooks"; deleting it stays allowed (it only costs one probe). The rule's known limits (ROADMAP) are unchanged; with a name-only cache, a write that gets past them can only pick among `python3`, `python` and `py -3` as PATH resolves them — it can no longer name a program.
- **bash-guard's destructive-SQL rule is linear.** It rescanned the rest of the command from every position, so its time grew with the square of the command's length: 16 KB of ordinary text took 12 s on the author's laptop. It is anchored now, with the same matches (rules are searched with `re.S`), and that command takes under a second.
- Tests: the launcher cases rewritten in their slots, 9 new (a 0.5.0 path cache, a word with a tail, an empty file, a Store alias, a symlinked file, a non-executable hit, an env var named `python` under bash 3.2, a FIFO, an upper-case `WINDOWSAPPS`; the symlink and FIFO cases run on Linux and macOS), 16 file-guard and 12 bash-guard cases (one is a 64 KB timing case) — `run 138 · ledger 46 · until-done 40 · file-guard 26 · heartbeat 114 · ab 36 · watch 63 · wait 187`, green in CI on Linux (Python 3.9 and 3.12), macOS and Windows. Checked on the author's Windows laptop: a 0.5.0 cache became `python` on the first event, five hook calls took 0.44–0.58 s each after, and a headless session with the dev plugin was denied both the Bash write and the Write of the file, with the human-only reason.

- **`hooks/watch.py`** — the watcher a session runs in the background after it hands work to another session, so a durable signal wakes it instead of a chat message that can be lost (case study 8: a "step done" message that never arrived; design `docs/notes/one-session-design.md`, M1). `--git <remote> <branch> [--path <file>] [--since <sha>]` fires on the push (with `--path`, once the file is in the pushed head); `--file <path>` on a file; `--max` (default 4h) ends it with `no signal after …` (exit 3) so the session is woken either way; three failed polls in a row end it with `cannot reach …` (exit 4), never a silent spin. `--since <the hand-off's commit>` catches a push made before the watcher started (armed late, or re-armed after a restart). 0 model tokens while waiting; no shell, every git call time-limited, credentials in URL remotes masked, laptop sleep handled (wall and monotonic clock). 63-case suite with a replay of the incident; in `all.sh` and CI.

## 0.3.0 — 2026-10-22, "a receipt per plan step"
- **One receipt per plan step.** `run-plan` marks the unit it is about to run as `running`; the `SubagentStop` hook attaches that agent's real API calls and tokens (`agent_calls`, `agent_input`, `agent_output`, `agent_models`, `agents`) to that unit in `routing.json` — never estimated, never guessed (two running units → the receipt line stays unattached). Build and verify agents on the same step accumulate. The unit also records the user's retier as `override: {from, to, by}`, the one escalation, and the fresh-agent verdict `verify: no gaps | gaps fixed | gaps open`.
- **`/smartuse:receipts [task|all]`** — new skill, 0 model tokens to compute: one row per plan step (`# · step · tier · model · override · outcome · esc · verify · calls · in · out · check`) plus the delegated share ("delegated out 4.0k, 100% of agent output on sonnet"). Closed runs are archived by the Stop hook under `~/.claude/smartuse/projects/<repo>/runs/<started_at>_<task>.json`, so a task's receipts outlive the next run.
- `run-plan --until-done`: the lazy-CEO loop. A Stop hook (`until-done.py`) refuses to end the turn while units or the repo's `check` command are unfinished; the model stops only for a real human question (`needs_human`), a double failure, a rule gate, or after 6 blocks. 22-case test.
